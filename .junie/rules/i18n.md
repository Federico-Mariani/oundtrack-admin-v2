# Internationalization (i18n) rules

Internationalization uses **Transloco** (`@jsverse/transloco`, the modern `@jsverse`
namespace) with the standalone APIs (`provideTransloco`, `provideTranslocoScope`,
`TranslocoDirective` / `TranslocoPipe`). No NgModule is created for Transloco. The Auth
feature is the reference implementation.

The guiding principle:

> Translations belong to the UI / bounded context that owns the text.

There is **no** giant global `en.json` / `it.json`. Feature UI → feature translations,
app shell → app presentation translations, shared UI component → that component's
translations, technical configuration → `core/i18n`.

## Supported languages

- Supported languages: **`en`, `it`** only. Nothing else is configured.
- Default **and** official fallback: **`en`**. A missing Italian key falls back to English
  (`missingHandler.useFallbackTranslation: true`), so behavior is predictable.
- The single typed source of truth is `core/i18n/supported-language.ts`
  (`SUPPORTED_LANGUAGES`, `SupportedLanguage`, `DEFAULT_LANGUAGE`, `LANGUAGE_OPTIONS`,
  `isSupportedLanguage`, `normalizeLanguage`). Never hard-code `'en'` / `'it'` elsewhere.
- Languages are **not** locales: no `en-US` / `it-IT`. If locale-aware formatting is needed
  later, map a language → locale in one place.

## File format

- **JSON only.** No XML / XLIFF / `.pot` / `.xlf` and no generated translation junk in the
  repo. JSON must be valid (no comments) and Prettier-formatted.
- The `en` and `it` variant of a given area keep the **same structure** (same key tree).

## Where translations live (ownership)

| Owner                               | Location                                             | Scope                   |
| ----------------------------------- | ---------------------------------------------------- | ----------------------- |
| A feature's pages / areas           | `features/<feature>/presentation/i18n/<lang>/*.json` | `provideTranslocoScope` |
| App shell (layouts, global errors)  | `src/app/presentation/i18n/<lang>/*.json`            | root / app scope        |
| A truly autonomous shared UI widget | co-located `i18n/` next to the component             | its own scope           |
| Technical Transloco configuration   | `core/i18n/`                                         | —                       |

- **Primary convention** for a feature: `features/<feature>/presentation/i18n/<lang>/<area>.json`
  (`en/common.json`, `en/login.json`, …). `common.*` holds text shared **inside** that feature,
  never app-global text.
- A genuinely autonomous shared UI component may co-locate its own `i18n/`. Choose one
  convention per component and do not randomly mix central feature i18n and component-local i18n.
- Feature translation resources are **implementation details**: they are NOT exported from the
  feature public API (`index.ts`). A feature registers its own scope in its routing.

## Scopes, splitting and loaders

- Each feature owns a Transloco **scope** named after the feature (`auth`, `home`, …). Keys are
  then `auth.common.*`, `auth.login.*`, … Do not add a redundant `auth` namespace inside the JSON (that would produce
  `auth.auth.*`).
- A scope may be split into several small, cohesive JSON files by meaningful area (`common`, `login`, `register`, …) —
  **not** one file per component (`login-title.json`, `login-button.json`). Split by translation ownership, keep files
  cohesive.
- Splitting is composed by the single shared primitive
  `core/i18n/scope-translation-loader.ts#composeScopeLoader`: feature loaders only **declare which
  files** compose their scope; each file becomes a top-level namespace under the scope. Do not
  duplicate merge logic per feature and do not build an internal i18n mini-framework.
- Each feature has an explicit, small, type-safe loader, e.g.
  `features/auth/presentation/i18n/auth-translations.loader.ts`, using **static** inline
  `import('./<lang>/<area>.json')`. No filesystem scanning, globbing, runtime reflection or
  magic naming.

## Lazy loading

- Feature translations are **lazy**: the scope is provided on the feature route subtree via
  `provideTranslocoScope({ scope, loader })` (see `auth.routes.ts`), so a feature's JSON is only
  fetched when the user enters that feature. Define the scope at the highest route that owns it;
  do not duplicate the provider on every page.
- The **root loader** (`core/i18n/transloco.providers.ts#RootTranslocoLoader`) loads only global
  app-shell translations (currently none → empty). It must NEVER know about any feature. There is
  no central loader enumerating every feature's JSON.

## Configuration & language lifecycle

- Transloco is configured **once** at the composition root through
  `core/i18n/transloco.providers.ts#provideAppTransloco()` (registered in `app.config.ts`):
  `availableLangs: ['en','it']`, `defaultLang: 'en'`, `fallbackLang: 'en'`,
  `reRenderOnLangChange: true` (runtime switch without full reload), `prodMode: !isDevMode()`.
- `core/i18n/language.service.ts#LanguageService` is the small, application-wide UI capability to
  read / change the active language. Transloco remains the **source of truth**; the service only
  resolves the initial language, applies changes and mirrors them (persistence + `<html lang>`),
  exposing a read-only `activeLanguage` Signal. No NgRx store for the language, no
  `LanguageFacade` / `LanguageStore` / `LanguageRepository`, no DDD aggregate for a UI preference.
- Initial language resolution is deterministic: **stored preference → browser language → English**.
  `it-IT` normalizes to `it`; `fr-FR` falls back to `en`.
- Persistence: `core/i18n/language-storage.ts` with the centralized key `LANGUAGE_STORAGE_KEY`
  (`'app.language'`); invalid stored values are ignored. All browser globals (`localStorage`,
  `navigator.language`, `document.documentElement.lang`) are accessed only there, SSR-safely.

## Layer boundaries (what may translate)

| Layer                                                                     | Transloco | Enforcement                 |
| ------------------------------------------------------------------------- | --------- | --------------------------- |
| `domain`                                                                  | ❌        | ESLint (restricted-imports) |
| `application` (ports/tokens/state), facades                               | ❌        | ESLint (restricted-imports) |
| `infrastructure`                                                          | ❌        | ESLint (restricted-imports) |
| `shared/types`, `shared/state/request` (shared-pure)                      | ❌        | ESLint (restricted-imports) |
| `presentation`                                                            | ✅        | allowed                     |
| `core/i18n`                                                               | ✅        | allowed                     |
| composition roots (`app.config.ts`, `<feature>.providers.ts`), `testing/` | ✅        | allowed                     |

- Domain and application expose **semantic error codes / structured data**, never localized text (`AuthError.code`, not
  a translated message). Presentation maps a code → translation key
  (`features/auth/presentation/i18n/auth-error-translation-key.ts`); the store keeps the code,
  not the key. `AuthError` is never modified to carry English/Italian text.
- Infrastructure maps backend failures to domain/application errors; it never translates UI text.

## Keys, copy and templates

- Keys describe **meaning / ownership**, not the English content: `auth.login.title`,
  `auth.login.actions.submit` — never `loginToYourAccount`, `clickHere`, `blueButtonText`,
  `text1`. JSON is nested and semantic, not `LOGIN_TITLE_TEXT`.
- Only translate user-visible text. Never put technical identifiers in JSON: API/route paths, CSS
  classes, form-control names, technical enum values, analytics event names. Routes stay stable and
  language-independent.
- Folder/file names stay in **English** (`login.json`, `common.json`) — the language is the
  content, not the code structure.
- In templates prefer the `TranslocoDirective` (`*transloco="let t; prefix: '<scope>'"`) when a
  template has several translations; the pipe is acceptable for a single simple case. Do not mix
  three approaches at random. Use interpolation for dynamic values (never string concatenation) and
  Transloco pluralization for quantities. Avoid HTML inside JSON and never `innerHTML` a translation.
- In TypeScript use the Transloco API (reactive `selectTranslate` when a lazy scope may not be
  loaded yet). Do not wrap the whole Transloco API in a `TranslationService` / `TranslationFacade`.

## DRY — the correct kind

Semantic behavior is shared, not identical words. Two features may each define `"cancel": "Cancel"`
if they belong to different contexts; a textual coincidence does not create shared ownership. A
translation moves to `shared` only when the UI concept is genuinely shared — not because a string is
used twice. A feature must never import another feature's i18n resources.

## Adding a new feature (checklist)

1. `features/<feature>/presentation/i18n/<lang>/<area>.json` (EN + IT, same structure).
2. `features/<feature>/presentation/i18n/<feature>-translations.loader.ts` using
   `composeScopeLoader` and static `import()`s.
3. `provideTranslocoScope({ scope: '<feature>', loader })` on the feature route subtree.
4. Use `TranslocoDirective` with `prefix: '<feature>'` in the pages.
5. Keep error → key mapping in presentation; keep domain/application code-only.

All of the above is partly machine-enforced (ESLint layer boundaries + project structure) and
partly convention (ownership, splitting, key naming) that reviewers and agents must uphold.
